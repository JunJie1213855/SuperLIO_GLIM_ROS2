# 异步回环后端

2026-10-27：`std_teaser_gicp` 和原有 `std_icp` 均使用以下流水线。

```text
关键帧回调（顺序维护 STD）
  点云过滤 → 描述子生成 → 候选检索/验证 → 插入描述子
  保存关键帧 → 添加里程计图节点 → 发布当前轨迹/三角形
  提交候选快照 ────────────────┐
                               ↓
配准工作线程：有界待处理队列 → TEASER++ / GICP 或旧 ICP
                               ↓
                      迟到回环边提交到已有图
                      刷新所有位姿和最新帧输出
                               ↓
地图工作线程：最新待处理位姿快照 → 重建并发布 /lio_slam/map
```

## 所有权与同步

- ROS 默认互斥回调组顺序执行关键帧回调；STD 数据库及滑窗仅由该回调修改。
- 配准任务复制窗口、原始位姿和共享点云指针，不读取 STD 数据库或实时 `frames_` 容器。点云保存后不再修改。
- 配准不持有图锁。iSAM2 的里程计节点插入、迟到回环边提交及位姿发布使用同一个图互斥锁，因此图优化仍可能短时阻塞入口；这不是完全无锁或硬实时系统。
- 正常关键帧先加入里程计图；回环结果使用原任务的 `(historical, current)` 索引连接已有节点，不重复插入初值。
- 回环更新后刷新历史位姿，使用当前最新节点重新计算 `map→world`，发布最新节点里程计及完整轨迹，避免倒退到旧任务帧。
- 已有图的迟到约束需要及时重线性化：iSAM2 使用阈值 0.01、检查间隔 1；回环提交强制重线性化/完整线性求解，并增加三次空更新以刷新鲁棒权重。这不是全图 batch 优化。
- TF 定时回调仍独立运行。实时 `map→world` 统一在发送锁内读取节点时钟，点云/轨迹仍保留传感器时间；播放 bag 应使用 `use_sim_time:=true` 和 `--clock`。

## 队列与过载

`registration_queue_capacity: 2` 表示最多 **2 个待处理任务**，另有最多 1 个运行中任务。任务可以包含多个候选，但仍受 `std_registration_top_k` 和软耗时预算限制。队列满时淘汰最旧的待处理检测任务，保留最新任务；不会删除已保存的关键帧、STD 描述子或里程计图节点，也不会强杀运行中的求解器。因此过载会降低回环检测覆盖率。

地图只有 1 个运行中快照和 1 个待处理快照。新请求覆盖待处理快照。快照包含一致的优化位姿和共享点云引用，重建不持有图锁。运行中的旧快照可能先发布，之后由最新快照替换；单地图线程保证完成结果不会乱序倒写。回环立即请求地图重建，普通关键帧沿用 `map_publish_stride`。

ROS 入口仍有 KeepLast(200) 的有限接收历史；本次拆分消除了配准/地图重建对描述子生成的直接串行等待，不能保证任意输入速率下都不丢消息。若 STD 本身处理时间超过关键帧周期，仍需要调整关键帧密度或优化 STD。

## 性能观测

普通日志每 5 秒最多输出一次对应位置的指标：

- `Backend timing`：点云过滤、描述子生成、检索/验证/插入、入口总耗时、消息时间年龄、待处理任务数和累计淘汰数。
- `Registration timing`：排队等待及配准/回环提交总耗时；软预算不包含排队等待。
- `Registration queue full`：过载淘汰提示，仅淘汰检测任务。
- `Map timing`：地图快照排队时间与重建时间。

`stamp_age` 只有在节点时钟与消息时间处于相同时间域时有意义。STD 已通过的候选与配准决策继续保留 INFO，检索明细和内部重试为 DEBUG。

## 验证方法

`test/async_backend_smoke.py` 使用真实 STD/TEASER/GICP 处理突发关键帧，检查图节点完整、有界队列淘汰、迟到约束、最新帧位姿以及地图输出。它使用专门的合成数据门限（2 帧窗口、内点比例 0.2、粗配准 RMSE 0.35 m），不改变默认参数，也不代表 UrbanNav 上的配准准确率。

`test/online_loop_smoke.py` 已改为按输入时间戳等待输出，并等待异步回环结果，避免把重复发布的当前位姿误计为新关键帧。

节点退出时唤醒并等待两个工作线程结束，不分离后台线程。未开始的任务在节点销毁时放弃；若要导出完整优化结果，应先等待检测和地图任务排空，再停止节点。

## 回环时间间隔门限

`loop_min_time_separation_s` 默认为 **30.0 秒**，两种配准模式都要求：

```text
当前候选关键帧的传感器时间戳 − 历史候选关键帧的传感器时间戳 > 30 秒
```

恰好 30 秒也拒绝。比较先对整数纳秒作差，不使用墙钟、消息排队时间或回放耗时。
近时间候选在几何验证/配准之前被过滤，后台执行及最终提交回环边时再次检查。
旧 STD+ICP 模式也在 STD 候选验证之前应用筛选，以免最佳近邻候选遮蔽合格历史候选。

此参数控制一个回环两端的时间距离；原 `loop_min_interval` 仍是连续接受回环之间的关键帧数冷却，两者共同生效。关键帧、描述子和里程计图节点仍正常插入，不因时间太近被删除。

## 临时使用空间距离检索

`loop_candidate_mode` 现默认 `distance`，可通过公共 launch 参数切换为 `std`。
`loop_candidate_radius_m` 默认 15 m，也作为公共 launch 参数提供。

距离模式在连续的原始 LIO/odom 坐标系中比较历史帧与当前帧的位置，先过滤
时间差不大于 30 秒的帧，再按距离升序选择候选。最多选择
`std_registration_top_k` 个候选（沿用现有参数名），已选候选邻近的两个索引
被抑制以避免重复尝试同一区域。不会混用优化后的历史位姿与未优化的当前位姿。

此模式不生成/插入 STD 描述子，也不要求 STD 三角形验证通过；注册窗口、
独立配准线程、图更新和异步地图仍保留。初值为 `O_h^{-1} O_c`，新模式将其
用于 FPFH 局部匹配提示，失败时仍可重试无提示 TEASER++。旧 ICP 模式也可使用
距离检索及该初值。粗/精配准质量门限没有降低。

距离模式依赖 LIO 漂移仍处于检索半径内；空间接近仅是候选，并不代表回环。
日志的 `Distance candidate` 表示实际开始验证距离候选，配准通过后才出现
`Loop ... accepted`。尚未执行的排队候选只输出 DEBUG。

示例：

```bash
SUPERLIO_WARN_MISSING_TIME=0 ros2 launch super_lio_slam vlp32.launch.py \
  loop_candidate_mode:=distance loop_candidate_radius_m:=15.0 \
  loop_registration_mode:=std_teaser_gicp use_sim_time:=true
```

恢复 STD：`loop_candidate_mode:=std`。候选模式在启动时读取，修改后需重启。

UrbanNav 独立片段试验另提供 `config/loop_distance_teaser_gicp.yaml`：只将粗
内点 RMSE 上限从 0.3 m 调到 0.4 m，内点比例 0.3、最少内点、空间分布和
GICP 门限保持原值。显式传入 `registration_config` 才启用；默认配置不变。
从第 100 秒开始重放的该试验接受了 3 条回环（详情见验证报告），不代表真值精度结论。
